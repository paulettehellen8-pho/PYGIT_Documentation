IN ONE SENTENCE

PyGit TUI is a terminal dashboard that lets developers see their Git status, stage files, view diffs, and run common Git commands — without memorizing flags or leaving the keyboard.

02 · Target Users

Target Users

PyGit TUI is aimed at people who use Git regularly but find the raw CLI unforgiving:

  • Junior developers and students who are still building confidence with Git commands and benefit from seeing status, branches, and diffs all at once.
  • Bootcamp / university cohorts working on group repositories, where merge conflicts and staging mistakes are common early mistakes.
  • Terminal-first developers who want a lightweight, no-GUI-install alternative to tools like GitHub Desktop, without needing the full feature set of established tools like lazygit or tig.
WHY THIS MATTERS

Git's CLI is powerful but unforgiving — a single wrong flag can lose work. A visual, keyboard-driven dashboard reduces that risk while still teaching the underlying commands (every action is logged verbatim in the command log).

03 · Problem Statement

Problem Statement

Git is the industry-standard version control system, but its command-line interface presents real friction for newer developers:

  • Core actions (staging, diffing, stashing, branching) each require separate commands and flags, which are easy to forget or mistype.
  • There is no single view that shows file status, branch state, recent commits, and stashes together — developers must run several commands just to get their bearings.
  • Merge conflicts are especially intimidating for beginners, who often don't know whether it's safe to continue or abort.
  • Existing polished solutions (e.g. lazygit) are excellent but are written in Go and are effectively "black boxes" to a Python-focused learning team — there's little room to learn from or extend them in a class setting.
04 · Proposed Solution

Proposed Solution

PyGit TUI re-creates the core experience of a terminal Git dashboard, in Python, using the Textual framework. It wraps everyday Git commands behind a live, two-column terminal interface so a developer can see everything relevant to their repository at a glance and act on it with single keystrokes.

👁

See

Live status, file changes, branches, commit history, and stashes — refreshed automatically.

⌨

Act

Stage/unstage, commit, stash, switch or merge branches, pull and push — via keybindings and a command palette.

🛟

Recover

A dedicated conflict view with abort/continue controls for merges, plus a raw command runner for anything not yet covered.

05 · Objectives

Objectives

  • Provide a single-screen, always-current view of a Git repository's state.
  • Let users stage, unstage, and commit changes without typing raw Git commands.
  • Support the most common day-to-day Git operations (stash, branch switch, merge, pull, push) through a lightweight command palette.
  • Make merge conflicts easier to navigate, by clearly listing conflicted files and offering guided abort/continue actions.
  • Keep a visible, honest log of every underlying Git command run, so the tool never hides what it's actually doing — supporting learning, not just convenience.
  • Build the whole tool as a fair, junior-appropriate scope: fewer features than lazygit, but each one working reliably.

07 · System Architecture

System Architecture

LayerTechnology
LanguagePython 3
Terminal UI frameworktextual (widgets, reactive state, modal screens, CSS-like styling via .tcss files)
Git integrationPython subprocess module, shelling out to the system git binary — no third-party Git library
Stylinggit_tui.tcss — Textual's CSS-like stylesheet controlling the two-column layout
Entry pointlg.py — defines the LazyGit Textual app and all panels/modals

The design deliberately separates concerns: git_checker.py holds every function that talks to Git (status, diff, commit, branch, stash, merge, conflict detection), while lg.py is purely responsible for UI. This keeps the Git logic testable and reusable independent of the interface.

08 · System Workflow

System Workflow

  1. User runs the app from inside a Git repository; the dashboard confirms repo status and populates all panels.
  2. User browses changed files and previews diffs by highlighting entries in the file list.
  3. User stages or unstages files with space as needed.
  4. User presses c to commit, types a message in the modal, and confirms — the commit runs and the dashboard refreshes.
  5. For anything beyond committing, the user opens the command palette (:) to stash, switch branch, merge, pull, or push.
  6. If a merge produces conflicts, the conflict panel appears automatically, listing affected files until resolved and the merge is continued or aborted.
  7. Throughout, the command log records every underlying Git call and result, and can also accept free-form commands directly.
09 · User Interface Design

User Interface Design

A single terminal screen split into two columns, plus modal overlays for focused input:

Main Dashboard

  • Left column: repository status, file list (staged/unstaged), branch list, commit history, stash list.
  • Right column: diff viewer, merge-conflict panel (shown only when relevant), command log with an inline command runner.

Modals

  • Commit modal: single text input for the commit message.
  • Command palette: selectable list of common Git operations, each with a single-letter shortcut.
  • Branch input modal: text input for a branch name, used for switch and merge.

Global keybindings include d to toggle light/dark theme, c to commit, and : to open the command palette — echoing familiar patterns from vim and lazygit for a low-friction learning curve.

11 · Future Enhancements

Future Enhancements

Deliberately out of scope for the current MVP, but reasonable next steps:

  • AI-assisted prompting — using an AI API to suggest commit messages from staged diffs, or to explain a merge conflict in plain language.
  • A visual commit graph for branch history, rather than a flat log.
  • Interactive rebase support.
  • Config file support for custom keybindings, similar to lazygit's.
  • Packaging as an installable CLI tool (e.g. via pip) rather than running the script directly.
12 · Project Impact

Project Impact

WHY THIS PROJECT IS WORTH BUILDING

It tackles a genuine pain point — Git's steep CLI learning curve — with a scope that's realistic for a junior team: not trying to out-build lazygit, but to understand and reproduce its core ideas in a language the team already knows well. It also doubles as a learning exercise in terminal UI design, process management via subprocess, and state-driven interfaces via Textual's reactive model.

13 · Conclusion

Conclusion

PyGit TUI takes a well-known problem — the friction of the raw Git CLI — and addresses it with a scoped, working Python terminal application. It is explicitly inspired by lazygit as a category of tool, not a copy of it, and the current build already covers the core loop a developer needs day-to-day: seeing repository state, staging and committing changes, handling branches and stashes, and recovering from merge conflicts.

The next additions — AI-assisted prompting and a completed task breakdown — will round out the proposal into a fuller submission.
